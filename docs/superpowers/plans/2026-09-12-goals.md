**Goal:** Goals you save toward — emergency fund, hajj, education, retirement, a holiday — each funded by the purchases you tag to it and the money you set aside, with what it needs every month against what you have set up.

**Architecture:** `packages/core` gains a `goals` module: units per goal from the tag on each buy, and the goal maths (cost growth, expected return, stages, the monthly amount needed, fitting goals to what you can save). `packages/db` gains migration `0008`, the goal tables, a goal column on trades and monthly buys, and repositories that tag a buy in place, check a sell against the goal's own units, and assemble each goal's plan. `apps/web` gains the Goals tab and the goal selects on Buy & sell, the asset detail and the monthly buy form.

**Tech Stack:** unchanged (TypeScript 7, Vitest 5, Drizzle sqlite-proxy, better-sqlite3 in tests, Vite 8, React 19, TanStack Router/Query, Tailwind 4, Playwright). No new dependencies.

## Global Constraints

- Money stays 64-bit integer minor units; units stay `units_micro` integers. No floats in stored values.
- A goal is tagged **per buy transaction**, never per whole asset: one holding can fund several goals.
- A sell names the goal its units come from and can never exceed that goal's units on that date.
- Changing a buy's goal updates the trade in place and writes an audit row. Goals are not ledger data, so nothing is voided.
- Money set aside from a savings account is an amount, never units, and above the balance it warns instead of blocking.
- Goals never change net worth, the balance sheet, the health ratios or the Coretax report.
- Rates are stored in basis points (`growth_bps`, `return_bps`), and 0% is allowed.
- Every task ends green on `npm test` and `npm run typecheck` at the repo root; web tasks also run `npm run e2e`.
- Commits end with the project trailer: `Co-Authored-By: Claude Opus 5 (1M context) <noreply@anthropic.com>`.

```ts
  id: string; name: string; kind: GoalKind; rank: number;
  growthBps: number; returnBps: number;
  standingMonthlyMinor: number; standingNote: string | null;
  stages: GoalStage[];
}
export interface GoalLink {
  accountId: string; name: string;
  kind: 'tagged' | 'earmark';
  unitsMicro: number | null;
  valueMinor: number;
  risk: Risk | null;
}

export interface StagePlan {
  stageId: string; name: string; dueOn: string; months: number;
  todayMinor: number; targetMinor: number; state: StageState;
}
export type GoalStatus = 'funded' | 'on_track' | 'behind';
export interface GoalPlan {
  goalId: string;
  currentMinor: number; totalTargetMinor: number;
  stages: StagePlan[];
  requiredMonthlyMinor: number; plannedMonthlyMinor: number;
  status: GoalStatus; shortfallMonthlyMinor: number;
  riskWarning: string | null;
}
export function goalPlan(
  goal: Goal, links: GoalLink[], plannedMonthlyMinor: number,
  monthlyOutgoingMinor: number, today: string,
): GoalPlan;
export interface RankFit { goalId: string; fundedMonthlyMinor: number; fits: 'full' | 'partial' | 'none' }
export function fitByRank(plans: GoalPlan[], goals: Goal[], capacityMonthlyMinor: number): RankFit[];
export function futureValueMinor(presentMinor: number, rateBps: number, months: number): number;
export function monthlyNeededMinor(gapMinor: number, rateBps: number, months: number): number;
```

Rules: months to a date are `max(1, round(days / 30.44))`. A stage's target is `futureValueMinor(todayMinor, growthBps, months)`, where an emergency stage's `todayMinor` is `targetMonths × monthlyOutgoingMinor`. Stages run in date order: a paid stage is skipped with state `paid`; otherwise the value carried so far grows at `returnBps` and, if it covers the target, the stage is `covered` and the surplus is discounted back to today and carried on; the first stage not covered is `saving` and sets `requiredMonthlyMinor` from `monthlyNeededMinor`; every stage after it is `later`. `monthlyNeededMinor` is the level payment of a future-value annuity, and with a 0% return it is the gap divided by the months. Status is `funded` when nothing is needed, `on_track` when planned covers at least 98% of what is needed, otherwise `behind` with the shortfall. `riskWarning` is set when the last unpaid stage is under 36 months away and a linked holding is high risk. `fitByRank` walks goals by rank, giving each what it needs until the capacity runs out; the one that runs out mid-way is `partial`.

- [ ] Tests (fail first): `futureValueMinor grows money at the rate given`; `futureValueMinor with 0% returns what went in`; `monthlyNeededMinor matches a known annuity figure`; `monthlyNeededMinor with 0% splits the gap evenly`; `an emergency goal targets months of spending and debt payments`; `a single-stage goal needs nothing when its links already cover it`; `a two-stage goal: the first is covered and the surplus carries to the second`; `the first uncovered stage sets the monthly amount, later ones say later`; `a paid stage is skipped`; `status is on track when the planned amount covers what is needed`; `status is behind with the shortfall per month`; `a goal due in a year holding shares gets a risk warning`; `a long goal holding shares gets none`; `fitByRank funds by rank until the money runs out`; `fitByRank marks the goal that only partly fits`.
- [ ] Implement; run `npm test -w @expanses/core`; commit `feat(core): goal maths with stages and rank fitting`.

**Changed from the plan during execution**

- **Stages stay free-form.** The owner pointed out that hajj reguler, hajj plus and furoda pay in different steps, so no template forces two stages: every template opens with one and the form adds, renames and removes the rest. The spec was corrected to match before building.
- **`periodFlows` now counts a month only when money actually moved.** A month holding nothing but an opening balance used to count, which understated every monthly figure (capacity read Rp 7,5 jt instead of Rp 10 jt in the goal tests). A regression test pins the new rule, and the health ratios in slice 2 read truer for a new workspace because of it.
- `GoalLinkRow` carries `overBalance`, so the page can say which account was capped rather than recomputing it.
- `goalUnitsOf` drops a goal from `byGoal` once its units reach zero, which keeps "what each asset is for" free of empty rows.
- The sell check lives in `recordTrade` itself (`checkGoalUnits`), so a sell beyond a goal's units is refused before anything is posted, naming the goal.
- `attentionItems` gained an optional third argument, goals, so the Overview's needs-attention list carries goals that are behind and set-aside amounts above their balance.
